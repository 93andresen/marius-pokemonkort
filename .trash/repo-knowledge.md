## 1. What this repo is

A personal project (Danish/Norwegian context, prices in NOK) for **Pokémon card arbitrage on finn.no**:

1. **Scrape** FINN.no ads for Pokémon cards (search pages → individual ad pages, JS-rendered via `--js`)
2. **Parse** the raw captures into structured, machine-read fields
3. **Ingest** into a Google Sheet as an append-only ledger + current-state view
4. **Evaluate deals** (LLM-derived valuations vs. asking price → `deal_score` / kr-per-card)
5. **Track buying decisions** manually in the sheet (interest → purchase)

The active workstream is defined in [`scraper-parser-spec.md`](scraper-parser-spec.md) (202 lines). Everything else in the repo is raw scrape archives, downloads from a phone (S21 Silver), LLM-prompt history, and planning documents.

## 2. The core design: `scraper-parser-spec.md`

The spec (currently at repo root) contains the complete pipeline contract. Its central ideas:

### 2.1 The two-kind data-ownership rule (non-negotiable)

Every column/field in the whole system is exactly one of:

| Kind | Written by | On re-scrape |
|---|---|---|
| **Machine-read** (anchored extraction — matches or `MISSING`) | Parser only, **append-only** | New rows appended; old values never mutated |
| **Derived** — LLM interpretation (card-list structuring, valuation, deal score) | LLM passes, in labeled columns, **with provenance** (`input_excerpt`, `method`, `confidence`, `produced_at`, reproducible) | Regenerated by re-run, never hand-edited |
| **Derived** — human (interest, notes, condition judgment, buy decision) | Humans only | **Automation never writes these, ever** |

Single invariant: **a writer never touches a column owned by another writer.** Machine-read derivations (e.g. `total_cost_nok = price + shipping + trygg_betaling`) are still machine-read — same immutability rules.

### 2.2 Machine-read field anchors (from real captures)

Fields with exact anchors include: `finn_kode` (cross-checked against `adId=` in map URL), `title`, `status` (`Solgt`/`Inaktiv`/absent=Aktiv), `price_nok` (**first** `NNN kr` under `## Til salgs` only — never from "Mer som dette" similar-ads), `shipping_nok` (`Frakt fra NNN kr`), `trygg_betaling_nok`, `condition` (seller's raw claim), `lat/lon/postal_code` (from map-link query params — never geocode by name), `last_modified` (Norwegian `D.M.YYYY kl. HH:MM`), `favorite_count` (regex, **JS-only** — the reason `--js` is mandatory), `image_uuids/item_ref` (from gallery URLs), `gallery_count` (cross-check vs UUID count), `breadcrumbs`, `fiks_ferdig`, `description_raw`, `card_list_raw`.

Parser rules: anchor-based only (no heuristic fallbacks, no LLM filling gaps), cross-check dual anchors loudly, append-only with `scraped_at`, per-scrape `parse_quality` (`full/partial/failed`), `parser_version` stored per row.

### 2.3 Sheet architecture

- **`FinnAdsRaw`** — append-only, one row per scrape event per ad. Price history = multiple rows, never mutated cells.
- **`FinnAdsCurrent`** — one row per ad, upserted from Raw. `finn_kode` unique (validation + duplicate highlighting).
- Error-checking formulas flag: `image_count ≠ photos on disk`, MISSING required fields, card-count mismatches (real example: ad says "79 stk" in title, "**99** stk" in description — surface loudly, human decides).
- Sold-ad intelligence (comps): keep scraping inactive/sold ads → time-to-sell velocity + favorite-count demand signal → feeds the arbitrage model.
- Manual pipeline column `interest` (ignore/watch/contact/negotiating/bought) → `FinnPurchases` linkage into the plan doc's `Purchases`/`BulkAllocation` tabs.
- Config tab: base URLs, query list, frequency, request budget, folder root.

### 2.4 Extra suggestions in the spec (not in the base task file)

Notification layer; seller dimension tab; snapshot search-result pages; resumable scrape checkpoints; `parser_version` per row; price-drop alerts; currency discipline (NOK asking vs Cardmarket/TCGPlayer values — never blend, let `deal_score` compare); daily local CSV backup of the sheet; fixed raw-ad test fixtures; cost-of-acquisition backfill into `Purchases`.

### 2.5 Future / parked

**Photo-based extraction** (vision pass over ad photos to identify/count cards, detect holo/graded/condition) — explicitly *not for implementation yet*; current design just must not block it. This is what would enable true kr-per-card for bulk lots.

### 2.6 Open questions (from the spec, unanswered)

- Max finncdn image size (`1280w` confirmed; does `original`/`1600w` work?)
- Does the search page expose a total result count to assert pagination against?
- Run frequency and request-budget ceiling?
- Auto-archive inactive ads from `FinnAdsCurrent` after N days?
- Harvest "Mer som dette" (similar ads) as a discovery source?

## 8. Conventions, rules, and constraints observed in this repo

- **No deletions — archive instead.** Anything unwanted goes to `.trash/` inside the same directory it lived in (e.g. `droprates/x.md` → `.trash/droprates/x.md`).
- **Read-only discipline during the undo session:** only read git commands; the allow-listed script [`repo_overview.py`](repo_overview.py) enforces this (`rev-parse`, `status`, `log`, `diff-tree`, `ls-tree`, `count-objects` etc. only).
- **`uv run` for all Python** (`repo_overview.py` is stdlib-only, no PEP 723 block needed).
- **`prompts-notes/prompts.md` is off-limits** for agent reading (explicit user instruction, 2026-09-25).
- **Python env rules:** never `pip install`/`python`/`uv run --with`; dependencies go in the script via the uv-dependency-injector skill.
- **Google Sheets MCP is available** but the decided data flow is: plain script (`uv run`) → gspread/service-account or CSV staging for bulk; MCP for interactive inspection only.
- `.gitignore` has a marker line: *"Repo-Spesific ignores (ALL EDITS TO THIS FILE SHOULD BE BELOW THIS LINE)"* — repo-specific entries belong below it. Current file ignores `.autogit/`, `.history/`, `.vscode/`, envs, `*.exe`, `*.tmp`, syncthing artifacts, etc.
